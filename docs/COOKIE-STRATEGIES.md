# BOSS 直聘登录态获取方式调研

> 目的：评估在**不使用手工复制 cookie** 的前提下，还有哪些可行的登录态获取路径，以及各自对本项目的适配度。
> 调研对象：三个公开项目的实现思路（只做技术归纳，不复制其代码）。
> 合规前提：仅用于采集**本人账号可见**的公开岗位信息，遵守站点 robots 与用户协议；不绕过验证码、不伪造他人身份。

---

## 0. 一个必须先接受的事实

BOSS 的登录态**生命周期极短**。参考项目 `LiShui666/boss_jobs_spider` 的作者实测结论：

> 一个 cookie 仅支持进行 4-5 次详情获取，因此需要定时滑动点击来刷新 cookie。

这意味着：**任何"取一次 cookie 长期用"的方案都不成立**。方案设计的核心不是"如何取到"，而是"如何持续持有且不需要人频繁介入"。

另外两点经验也值得记录：

- 站点会禁止 F12 / 打开开发者工具即跳走（与本项目使用者遇到的现象一致），所以**依赖 DevTools 手工复制的方式本身就不稳定**。
- 风控码 `code 31` / `code 37`（"您的环境存在异常"）会被误判为"未登录"，判断登录态时不能只看 401。

---

## 1. 六种获取方式

| # | 方式 | 原理 | 需人工 | 稳定性 | 服务端可用 | 备注 |
|---|---|---|---|---|---|---|
| A | 手工复制 Cookie 头 | 从请求头整行复制 | 每次 | 低（4-5 次即失效） | 是 | 当前已支持（`--cookie-file`），只适合临时验证 |
| B | 浏览器扩展自动采集 | 扩展在页面上下文内读取并 POST 到自有服务 | 装一次 | 高 | 是（作为数据来源） | 登录态始终留在浏览器，最贴合长期使用 |
| C | CDP 附加已登录浏览器 | 通过 DevTools Protocol 连接真实 Chrome，旁听页面自身请求 | 首次登录 | 高 | 否（需在用户电脑上跑） | 参考项目 `eatmoreduck/boss-zhipin-scraper` 的主路线 |
| D | 自动化浏览器自行登录 | DrissionPage / Playwright 起浏览器、自动走登录 | 低 | 低 | 否 | 参考项目 `LiShui666/boss_jobs_spider`；指纹明显、易触发风控 |
| E | 本地逆向生成 `__zp_stoken__` | 用 Node 复现站点 JS 计算出该令牌 | 无 | 极低 | 理论上 | 参考项目 `lishunyi123h/q369696495`；站点 JS 一变即失效 |
| F | 导入浏览器 Cookie 数据库 | 复制 Chrome 的 `Cookies` sqlite（需系统级解密）到隔离 profile | 一次 | 中 | 否 | 参考项目 C 的 `--copy-login-state`；本质仍是凭据搬运 |
| G | 手机抓包 | 手机连代理装证书，从 App 流量里取 | 每次 | 中 | 是 | 适合临时取一次，不适合常态化 |

（另有一类"共享/租用 cookie 池"，涉及他人账号与协议风险，**不在建议范围内**，不展开。）

## 2. 对各方式的具体评估

### A. 手工复制 —— 已支持，但只是兜底

我们当前实现的 `--cookie-file` 就属于这一类。优点是零开发成本、服务端直接可用；
缺点是每次只能撑几次请求，且站点禁止 F12 让"取"这个动作本身都变得别扭。

**结论：保留为应急通道，不作为主路径。**

### B. 浏览器扩展 —— 与本项目最契合

扩展跑在用户自己的浏览器里，`fetch` 自动携带 cookie、`__zp_stoken__` 由页面自动刷新，
**用户完全不需要接触 cookie 字符串**。抓到的结构化数据通过自有接口回传服务端。

- 关键取舍：**扩展只做"取数"，不做"搬运凭据"**。不回传 cookie 值，只回传岗位 JSON。
- 与现有链路的关系：新增 `POST /api/ingest`（独立 token），数据仍走 `store.MergeAndSave` 去重与前端展示。
- 与"只保留 live 模式"不冲突：服务端的 `live` 是命令行入口，扩展是浏览器侧的第二条入口。

**结论：推荐作为长期主路径。**

### C. CDP 附加真实浏览器 —— 值得借鉴，但位置在"用户电脑"

参考项目的做法很聪明：不注入 XHR，而是**被动旁听页面自己发出的搜索请求**，
这样流量特征与真人操作一致，也能直接拿到明文的 `salaryDesc`，绕开前端字体混淆。

但它必须运行在**有浏览器的那台机器**上——我们服务端在云上，没有用户的浏览器可附加。
所以它正确的落位是：做成一个"本地采集助手"，用户在自己电脑跑，抓完把结果 POST 给服务器。

- 优点：不用装扩展，Python 脚本即可；复用真实指纹，稳定性高于自动化浏览器。
- 缺点：用户需要装 Python 环境、首次登录一次；仍然要"在电脑上"这个前提。

**结论：作为 B 的备选，适合不想装扩展的用户。**

### D. 自动化浏览器 —— 不推荐

DrissionPage/Playwright 起的是"受控浏览器"，指纹与真人有明显差异（参考项目为此专门改浏览器返回值，
因为"DP 默认浏览器返回内存为空会被识别"）。这类方案维护成本高、封号风险也最高。

对我们尤其不适用：**云服务器 IP 本身就是风控重点**，等于两个风险叠加。

### E. 本地逆向 stoken —— 不推荐

`__zp_stoken__` 由站点 JS 计算，逆向复现可行（参考项目 2020 年就做过），但它是**动态变化的**——
该 README 自己就写着"更新处理了动态 js 的变化"。一旦站点改算法，方案立即失效，需要有人持续跟进逆向。

对一个个人工具来说，这是把外部变化风险扛到自己身上，性价比最低。

### F. 导入 Cookie 数据库 —— 只适合"一次性迁移"

参考项目的 `--copy-login-state` 只复制 `Local State` 与 `Cookies*` 文件（不复制密码库、历史、扩展），
思路克制。但 Chrome 的 cookie 在磁盘上是系统级加密的，跨机器/跨用户解密未必可行；
且它解决的仍是"把凭据搬到另一个浏览器"，没有解决"持续有效"。

**结论：可用于把主浏览器登录态迁到专用 profile，不适合作为服务端方案。**

### G. 手机抓包 —— 临时手段

手机连代理（Reqable / Charles）+ 装根证书，能取到 App 端请求头里的 cookie。
适合"就想马上试一次"，但每次都要重复，且 App 与网页端的 cookie 体系不完全一致。

---

## 3. 结论与建议

**推荐组合（按优先级）：**

1. **B 扩展自动采集 + `POST /api/ingest`** —— 长期主路径，用户不接触 cookie；
2. **C 本地 CDP 助手** —— 给不想装扩展的用户，借鉴"旁听页面请求"的思路；
3. **A 手工 `--cookie-file`** —— 保留为应急与调试通道。

**明确不做的：**

- 服务端跑无头浏览器抓取（云 IP + 指纹双重风险，且违反 robots）；
- 本地逆向 stoken（持续维护成本远超收益）；
- 任何形式的 cookie 池 / 他人账号凭据。

**必须写进文档的限制：**

- 登录态生命周期极短（4-5 次详情请求量级），任何方案都要处理"失效即重取"；
- 风控码 `31` / `37` 不能当成"未登录"处理，否则会误导用户反复重登；
- 站点禁止 DevTools 的行为是既定事实，方案不能依赖它。
